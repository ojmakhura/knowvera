# JMeter tests for the knowvera API

Generated by `scripts/generate_jmeter.py` from the controllers, the role matrix
(`keycloak/generate_authz.py`) and the generated `@PreAuthorize` expressions. Do not edit the
`.jmx` files by hand; regenerate them after the API or the roles change:

```bash
python3 scripts/generate_jmeter.py
```

| Plan | What it checks |
|---|---|
| `knowvera-authorization.jmx` | Every endpoint for every sample user, against the outcome the permission rules predict. Public endpoints answer without a token, protected ones return 401 without one, and only `/actuator/health` and `/actuator/info` are served. |
| `knowvera-load.jmx` | Read-heavy journeys: a KYC analyst working through case lists, applicants checking their application, organisation administrators following their client requests. |

## Before running

1. **JMeter 5.6 or later** (the plans were checked with 5.6.3) ([jmeter.apache.org](https://jmeter.apache.org/download_jmeter.cgi)). The Ubuntu
   `jmeter` package (2.13) cannot load any test plan (`ForbiddenClassException: ScriptWrapper`).
2. **Keycloak with the test realm** (`webservice/src/test/resources/test-realm.json`): it has the
   sample users below and allows the password grant the plans sign in with. The deployable realm
   (`knowvera-realm.json`) turns that grant off on the portals.
3. **The API**, pointed at that Keycloak. For the load test, raise the per-user limit:
   every thread of a journey signs in as the same sample user, so with the default
   `RATE_LIMIT=2000` (per user per minute) larger runs get `429` responses.

## Test API on the local stack

`jmeter/test-stack.sh` runs a second API instance (port 18085) on the existing services, kept apart
from dev: Keycloak realm `knowvera-test` (import `results/test-stack/knowvera-test-realm.json` once),
Postgres database `knowvera_test`, RabbitMQ vhost `knowvera-test` and Redis database 1.

```bash
jmeter/test-stack.sh up
```

```bash
jmeter/test-stack.sh seed
```

`seed` (idempotent) gives `applicant` an individual profile and links `org.admin` to a client
organisation, which the load journeys need. Then run a plan with
`JMETER_ARGS="$(jmeter/test-stack.sh jmeter-opts)"`, and stop the API with `jmeter/test-stack.sh down`.

## Running

With the Makefile (JMeter at `/usr/local/apache-jmeter-5.6.3/bin/jmeter`, override with `JMETER=...`;
reports land in `results/`):

```bash
make jmeter_authz JMETER_ARGS="-JkeycloakUrl=http://localhost:8970"
```

```bash
make jmeter_load JMETER_ARGS="-JstaffThreads=10 -Jduration=600"
```

Or directly:

```bash
jmeter -n -t jmeter/knowvera-authorization.jmx -l results/authorization.jtl -e -o results/authorization-report
```

```bash
jmeter -n -t jmeter/knowvera-load.jmx -Jhost=localhost -Jport=8085 -JstaffThreads=10 -Jduration=600 -l results/load.jtl -e -o results/load-report
```

Open `results/*-report/index.html` for the HTML report. Every property can be set with `-J<name>=<value>`.

| Property | Default | Meaning |
|---|---|---|
| `protocol` | `http` | API protocol |
| `host` | `localhost` | API host |
| `port` | `8085` | API port |
| `keycloakUrl` | `http://localhost:8970` | Keycloak base URL |
| `realm` | `knowvera` | Keycloak realm |
| `password` | `Test-Passw0rd!` | Password of the sample users (test realm) |
| `unknownId` | `00000000-0000-4000-8000-000000000000` | Id of a record that does not exist |
| `anonymousPaceMs` | `2100` | Authorization plan: delay between anonymous calls, which are rate limited per IP (30 per minute) |
| `staffThreads` | `5` | Concurrent back-office users (KYC analyst journey) |
| `applicantThreads` | `5` | Concurrent applicants |
| `orgThreads` | `3` | Concurrent organisation administrators |
| `rampUp` | `60` | Seconds to start all threads |
| `duration` | `600` | Test length in seconds (keep below the access token lifetime, 900 s) |
| `thinkMin` | `500` | Minimum think time between requests (ms) |
| `thinkMax` | `2000` | Maximum think time between requests (ms) |

## Reading the authorization results

Each request is named `ALLOW` or `DENY` and its comment says why (e.g. *holds kyc-records:view*,
*holds only kyc-records:view-own; the record is not theirs*).

- **ALLOW** passes when the response is not 401, 403 or 429. Only `GET` endpoints are called on the
  allowed side, so the plan never changes data; with the non-existent `unknownId` they may answer
  404 or 500, which still proves authorization let the call through.
- **DENY** passes on 403. For `POST`/`PUT`/`PATCH`/`DELETE` it also accepts 400 or 415, because a
  request body or file part can be rejected before authorization runs.
- A failed `Sign in as ...` sample means Keycloak rejected the sample user (wrong realm or password,
  or the password grant is off); the rest of that role's requests will then fail with 401.
