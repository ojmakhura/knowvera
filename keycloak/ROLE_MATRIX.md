# knowvera-api role matrix

Generated by `keycloak/generate_authz.py`. Edit `GRANTS` / `SCOPE_RULES` there, not this file.

## Roles

Roles are hierarchical: a role has everything the roles it includes have (Keycloak composite roles).

| Role | Abbrev. | Includes | Description |
|---|---|---|---|
| `CUSTOMER` | CUS | `PORTAL_USER` (knowvera-web client role) | Base role of every external user: signs in to the portal, own records only |
| `APPLICANT` | APP | `CUSTOMER` | Individual applying for KYC: own profile, KYC application and documents |
| `ORG_USER` | OU | `CUSTOMER` | Member of a client organisation: its client requests and KYC cases |
| `ORG_ADMIN` | OA | `ORG_USER` | Administrator of a client organisation: also its users, branches and billing |
| `STAFF` | STF | `ADMIN_PORTAL_USER` (admin-portal client role) | Base role of every back-office user: signs in to the admin portal, reads reference data |
| `KYC_ANALYST` | KAN | `STAFF` | Captures KYC data and evidence, runs automated checks |
| `KYC_REVIEWER` | KRV | `KYC_ANALYST` | Reviews captured KYC cases and documents |
| `KYC_APPROVER` | KAP | `KYC_REVIEWER` | Takes the approve / reject decision on reviewed KYC cases |
| `SCREENING_ANALYST` | SA | `STAFF` | Screens subjects against sanctions, PEP and adverse media lists |
| `RISK_ANALYST` | RA | `STAFF` | Assesses and records customer risk |
| `AUDITOR` | AUD | `STAFF` | Reads and exports everything, including the audit trail |
| `COMPLIANCE_OFFICER` | CO | `KYC_APPROVER`, `SCREENING_ANALYST`, `RISK_ANALYST`, `AUDITOR` | Oversees KYC compliance and owns the KYC requirements configuration |
| `MLRO` | MLRO | `COMPLIANCE_OFFICER` | Money Laundering Reporting Officer: escalations and regulatory reporting |
| `CASE_MANAGER` | CM | `STAFF` | Routes client requests and KYC cases through the workflow |
| `FINANCE_OFFICER` | FO | `STAFF` | Manages subscriptions and invoices |
| `PLATFORM_ADMIN` | PA | `STAFF` | Configures the platform: settings, reference data, users, sequences |
| `SUPER_ADMIN` | SUP | `PLATFORM_ADMIN`, `MLRO`, `CASE_MANAGER`, `FINANCE_OFFICER` | Everything: platform administration and every business role (bootstrap, support) |
| `DEVELOPER` | DEV | `SUPER_ADMIN`, `APPLICANT`, `ORG_ADMIN` | Developer / tester: every back-office and external role, to exercise both portals with one account |

## Scopes

| Scope | Meaning |
|---|---|
| `self` | Read or change the caller's own data (my records, my profile) |
| `view` | Read a single record |
| `list` | List, page or search records |
| `edit` | Create or update a record (save is an upsert) |
| `delete` | Remove a record or one of its parts |
| `submit` | Start a KYC application or attach evidence to one |
| `verify` | Run automated checks: extraction, analysis, data verification, screening |
| `review` | Change the review/decision status of a case, document or request |
| `export` | Download files and generate reports |
| `import` | Bulk upload records or templates |
| `manage` | Grant or revoke user roles |

Each granted (resource, scope) is available to Spring as the authority `SCOPE_<resource>:<scope>`, e.g. `@PreAuthorize("hasAuthority('SCOPE_organisations:view')")`.

Owner-scoped roles (CUSTOMER, APPLICANT, ORG_USER, ORG_ADMIN) are granted `<scope>-own` instead of `<scope>` (shown as "own:" below), except on reference data. On endpoints annotated with `@RequiresOwnership` they must own the record; elsewhere a `-own` grant does not open the endpoint.

`self` is granted to every authenticated user and is left out of the table below.
